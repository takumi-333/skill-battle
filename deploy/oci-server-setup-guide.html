OCI Always Freeでオンライン対戦サーバーを公開する

Skill Battle の Dedicated Server（Godot/ENet）とLobby API（FastAPI）を、Oracle Cloud Infrastructureの無料ARM VMへ配備する初回手順です。作成日: 2026-09-09

この手順で公開するポート
  • UDP 7000: Godot Dedicated Serverへの対戦通信
  • TCP 80 / 443: Lobby APIをCaddy経由でHTTPS公開し、証明書を取得するための通信
  • TCP 22: SSH管理用。自分のグローバルIPだけから許可する
実行前の注意
  • コマンド中の <…> は実際の値へ置換する。
  • 秘密値・SSH秘密鍵・.envはGitへ保存しない。
  • SSHの許可元IPを誤ると、自分自身がVMへ接続できなくなる。UFWを有効にする前に必ず確認する。
  • Dedicated ServerはOCI Ampere A1向けのLinux ARM64 exportが必要。Windows版やLinux x86_64版は動かない。

0. 事前に決める値

項目例用途

公開ドメインgame.example.comHTTPS Lobby APIの接続先。ドメイン未取得なら先に用意する

解説を開く: なぜドメインとIPを分けるのか
Lobby APIはHTTPSのためドメインを使います。CaddyはそのドメインのTLS証明書を自動取得します。一方、ENetはUDPで接続するため、Lobby APIはクライアントへDedicated ServerのIPまたはドメインとUDPポートを返します。両者を同じドメインにしても問題ありません。

1. OCIでAlways Free VMを作成する

  1. OCIコンソールで Compute → Instances → Create instance を開く。
  2. Imageは Ubuntu の Always Free Eligible を選ぶ。
  3. Shapeを VM.Standard.A1.Flex に変更し、2 OCPU / 12 GB RAMを設定する。
  4. ネットワークは「新しいVCNとパブリック・サブネットを作成」を選び、パブリックIPv4の自動割当を有効にする。
  5. SSH公開鍵を貼り付け、Create を押す。作成完了後、表示されたパブリックIPを控える。
解説を開く: このVM設定で何が確保されるか

OCI Always FreeのAmpere A1枠は、合計2 OCPU・12 GBメモリまでを無料で割り当てられます。ARM64 CPUなので、Godotのサーバー成果物もARM64で作ります。パブリックIPv4はプレイヤーと管理PCがインターネット越しに到達するために必要です。

作成時に Out of host capacity が出るのは無料A1枠の空き不足です。Availability Domainを変更するか、時間を置いて再試行します。

2. OCI側のネットワーク・ファイアウォールを設定する

Networking → Virtual Cloud Networks → 対象VCN → Security Lists → Default Security List → Ingress Rules を開きます。既存の全公開SSHルールがあれば、削除または自分のIPへ制限します。

Source CIDRProtocolDestination portStateful説明
<管理元IP>/32TCP22はいSSH管理
0.0.0.0/0UDP7000はいオンライン対戦
0.0.0.0/0TCP80はいCaddyの証明書取得とHTTP→HTTPS転送
0.0.0.0/0TCP443はい公開Lobby API（HTTPS）
解説を開く: Security ListとOS側UFWの両方が必要な理由

Security ListはOCIネットワーク側の仮想ファイアウォールです。UFWはUbuntu VM内部のファイアウォールです。どちらか一方で遮断されると通信できません。二重に設定することで、誤設定時の露出を減らせます。

0.0.0.0/0は「全インターネットから」を意味します。プレイヤー用のUDP 7000と公開Web APIの80/443だけに使い、SSHには使いません。

3. SSH接続とUbuntu初期設定

Windows PowerShellから接続します。

ssh -i "$env:USERPROFILE\.ssh\oci_skill_battle" ubuntu@<VMのパブリックIP>

接続後、OS更新と必要な基本パッケージを入れます。

sudo apt update
sudo apt upgrade -y
sudo apt install -y python3 python3-venv python3-pip ufw openssl curl
解説を開く: ここで入れるもの
  • python3 / venv: FastAPIのLobby APIを専用仮想環境で動かすために使う。
  • ufw: Ubuntu側の受信ポート制御に使う。
  • openssl: トークン署名鍵・管理トークンをVM上でランダム生成する。
  • curl: APIの死活確認とCaddy導入に使う。

4. Ubuntu側のファイアーウォール（UFW）を設定する

最初にSSHの許可を入れてから有効化します。

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from <管理元IP>/32 to any port 22 proto tcp
sudo ufw allow 7000/udp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status numbered
解説を開く: 各UFW操作がすること
  • default deny incoming: 明示的に許可していない外部からの受信を拒否する。
  • default allow outgoing: OS更新、証明書取得、外部API利用などVMから開始する通信を許可する。
  • allow from … port 22: SSHを指定IPのみに絞る。先にこれを入れずにUFWを有効化すると接続を失う。
  • allow 7000/udp: Godot ENet通信を受け付ける。TCP 7000ではない点に注意。
  • allow 80/tcp と 443/tcp: CaddyがHTTPS証明書を取得・提供するために必要。

5. Dedicated ServerをLinux ARM64でexportする

  1. Windows上のGodotエディタで Project → Export を開く。
  2. Linux用プリセットを追加し、Architectureを arm64 にする。
  3. ResourcesタブのExport modeを Export as dedicated server にする。
  4. 出力先を例として build/server/skill-battle-server にし、Release exportを実行する。
解説を開く: なぜDedicated Server exportにするのか
Dedicated Server exportは、サーバーに不要な描画リソースを削減・置換でき、dedicated_server機能タグも追加します。サーバーは画面・GPUなしで実行でき、現在のsystemdサービスは --headless --scene res://scenes/server_main.tscn を付けて専用サーバーのシーンだけを起動します。

6. アプリケーションをVMへ配置する

ローカルPCから、export成果物・Lobby API・systemd定義をVMの一時ディレクトリへ送ります。

scp -i "$env:USERPROFILE\.ssh\oci_skill_battle" -r .\build\server\* ubuntu@<VMのパブリックIP>:/tmp/skill-battle-server/
scp -i "$env:USERPROFILE\.ssh\oci_skill_battle" -r .\server\lobby ubuntu@<VMのパブリックIP>:/tmp/
scp -i "$env:USERPROFILE\.ssh\oci_skill_battle" .\deploy\systemd\skill-battle-server.service .\deploy\systemd\skill-battle-lobby.service ubuntu@<VMのパブリックIP>:/tmp/
scp -i "$env:USERPROFILE\.ssh\oci_skill_battle" .\deploy\bin\skill-battle-control .\deploy\sudoers.d\skill-battle-control ubuntu@<VMのパブリックIP>:/tmp/

VM上で、アプリ用ユーザーと配置先を作り、成果物を移します。

sudo useradd --system --create-home --home-dir /opt/skill-battle --shell /usr/sbin/nologin skill-battle
sudo install -d -o skill-battle -g skill-battle -m 0750 /opt/skill-battle/server/current
sudo install -d -o skill-battle -g skill-battle -m 0750 /var/lib/skill-battle

sudo cp -a /tmp/skill-battle-server/. /opt/skill-battle/server/current/
sudo mv /tmp/lobby /opt/skill-battle/lobby
sudo chown -R skill-battle:skill-battle /opt/skill-battle /var/lib/skill-battle
sudo chmod +x /opt/skill-battle/server/current/skill-battle-server

sudo -u skill-battle python3 -m venv /opt/skill-battle/lobby/.venv
sudo -u skill-battle /opt/skill-battle/lobby/.venv/bin/pip install -r /opt/skill-battle/lobby/requirements.txt
解説を開く: 配置先と専用ユーザーの役割
  • /opt/skill-battle/server/current: 現在稼働させるGodotサーバー成果物。
  • /opt/skill-battle/lobby: FastAPIのソースとPython仮想環境。
  • /var/lib/skill-battle/lobby.db: 永続化するSQLiteデータ。アプリ本体とデータを分離する。
  • skill-battleユーザー: サービスをrootで実行しないための専用アカウント。

7. 秘密値と環境変数を設定する

秘密値はVM上で生成します。以下の3つを生成し、安全なパスワードマネージャーへ控えます。

openssl rand -hex 32

/etc/skill-battle/server.env を作成します。

SKILL_BATTLE_TOKEN_SECRET=<トークン署名用の秘密値>
SKILL_BATTLE_INTERNAL_API_TOKEN=<Dedicated Server→Lobby内部API用の秘密値>
SKILL_BATTLE_LOBBY_INTERNAL_URL=http://127.0.0.1:8000
SKILL_BATTLE_SERVER_PORT=7000

/etc/skill-battle/lobby.env を作成します。

SKILL_BATTLE_TOKEN_SECRET=<server.envと同じトークン署名用秘密値>
SKILL_BATTLE_INTERNAL_API_TOKEN=<server.envと同じ内部API用秘密値>
SKILL_BATTLE_ADMIN_TOKEN=<管理画面ログイン用の別の秘密値>
SKILL_BATTLE_SERVER_ADDRESS=game.example.com
SKILL_BATTLE_SERVER_PORT=7000
SKILL_BATTLE_LOBBY_DB=/var/lib/skill-battle/lobby.db

作成後はrootだけが書き換えられ、サービスユーザーだけが読める権限にします。

sudo install -d -m 0750 /etc/skill-battle
sudo chown root:skill-battle /etc/skill-battle/server.env /etc/skill-battle/lobby.env
sudo chmod 640 /etc/skill-battle/server.env /etc/skill-battle/lobby.env
解説を開く: 3種類の秘密値を分ける理由
  • SKILL_BATTLE_TOKEN_SECRET: ロビーが発行し、Dedicated Serverが検証する短命参加トークンの署名鍵。両サービスで同じ値にする。
  • SKILL_BATTLE_INTERNAL_API_TOKEN: Dedicated ServerからLobbyの/internal/*を呼ぶための内部認証鍵。外部公開しない。
  • SKILL_BATTLE_ADMIN_TOKEN: /adminの運用画面を操作するための鍵。ほかの鍵と共用しない。

8. systemdサービスを登録して起動する

sudo install -o root -g root -m 0644 /tmp/skill-battle-server.service /etc/systemd/system/
sudo install -o root -g root -m 0644 /tmp/skill-battle-lobby.service /etc/systemd/system/
sudo install -o root -g root -m 0750 /tmp/skill-battle-control /usr/local/sbin/skill-battle-control
sudo install -o root -g root -m 0440 /tmp/skill-battle-control /etc/sudoers.d/skill-battle-control
sudo visudo -cf /etc/sudoers.d/skill-battle-control

sudo systemctl daemon-reload
sudo systemctl enable --now skill-battle-lobby skill-battle-server
sudo systemctl status skill-battle-lobby skill-battle-server --no-pager
解説を開く: systemdを使う理由

systemdはOS起動時にLobby APIとDedicated Serverを自動起動し、異常終了時にはRestart=on-failureで再起動します。手動でターミナルを開き続ける必要がなく、ログもjournalctlへ集約されます。

skill-battle-controlとsudoers設定は、管理画面から許可済みのサービス操作だけを実行するための制限付きの橋渡しです。Lobby API自体をrootで動かしてはいけません。

9. CaddyでLobby APIをHTTPS公開する

既存の deploy/Caddyfile をそのまま使わない

現在のファイルにある ${SKILL_BATTLE_DOMAIN} はCaddyfileの環境変数記法ではありません。環境変数を使うなら {$SKILL_BATTLE_DOMAIN} と書き、Caddyのsystemdサービスへその変数を渡す必要があります。この初回手順では、誤設定を避けるため実際のドメインを直接記述します。

先にDNSで game.example.com のAレコードをVMのパブリックIPへ向けます。その後、Caddyを導入します。

sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy

/etc/caddy/Caddyfileを以下にします。game.example.comは実際のドメインへ置き換えます。

game.example.com {
    @internal path /internal/*
    respond @internal "not found" 404
    reverse_proxy 127.0.0.1:8000
}
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl enable --now caddy
sudo systemctl status caddy --no-pager
解説を開く: Caddy・80番ポート・internal APIの関係

Caddyは外部のHTTPS通信を受け、同一VM上でのみ待受しているLobby API（127.0.0.1:8000）へ転送します。ドメインがVMを指し、TCP 80/443が外部から到達できると、TLS証明書を自動取得・更新します。

/internal/*はDedicated Serverだけがloopback経由で利用する内部APIです。Caddyで公開しないことで、外部から試合状態や監視情報を勝手に更新されることを防ぎます。

10. 公開確認とクライアント設定

VM内でサービスとポートを確認します。

curl http://127.0.0.1:8000/healthz
systemctl status skill-battle-lobby skill-battle-server caddy --no-pager
sudo ss -lntup
journalctl -u skill-battle-lobby -u skill-battle-server -u caddy --since "10 minutes ago" --no-pager

管理PCからHTTPSを確認します。

curl https://game.example.com/healthz

公開用クライアントの lobby_api_url は、現在の既定値 http://127.0.0.1:8000 ではなく、https://game.example.com に設定してからexportします。

解説を開く: 最終確認で見るべきこと
  • /healthzが外部から {"ok":true} を返すこと。
  • 別ネットワークのPC 2台で、ロビー一覧 → ルーム作成 → 参加 → 対戦開始まで進めること。
  • Dedicated Serverのログに接続・切断イベントが出ること。UDPは単純なHTTP確認では検証できないため、実ゲームクライアントで確認する。
  • 管理画面は https://game.example.com/admin。公開するなら、さらにCaddyまたはOCIで管理元IPに絞ることを推奨する。
