# バグ調査レポート（2026-09-07）

## 調査概要

専用サーバー方式への移行後の Godot クライアント、Dedicated Server、Lobby API、SQLite 永続化を、仕様書・実装・既存テスト・簡易動的検証の観点から調査した。

今回の調査では実装修正は行っていない。以下の「再現済み」は調査用の一時実行で確認した結果、「コード上確実」は実装と仕様の経路から発生条件が明確なもの、「要追加検証」は実環境での統合確認が必要なものを表す。

## 優先度サマリー

| ID | 優先度 | 確度 | 概要 |
| --- | --- | --- | --- |
| BA-01 | 高 | コード上確実 | Dedicated Server が Lobby の状態更新を一度も送らず、60秒後にルーム一覧と実際のセッションが不整合になる |
| BA-02 | 高 | 再現済み | SQLite の共有接続とトランザクション競合により、同時参加予約が重複または例外になる |

## BA-01: Lobby 状態更新未接続によるルーム不整合

- **対象**: `scripts/network/dedicated_server.gd:14-171`、`server/lobby/app.py:48-52`、`server/lobby/database.py:20-24,53-59`
- **優先度**: 高
- **確度**: コード上確実。60秒超の試合で発生する統合不具合は要追加検証。

### 事実

仕様では試合終了・切断時に Dedicated Server が Lobby Server へ `open/running/closed` を通知することになっている（`docs/specs/オンライン対戦アーキテクチャとサーバー責務.md:38,77,90-91,121`）。しかし Dedicated Server には Lobby API へ HTTP リクエストを送る処理がなく、`room_status` の呼び出しも存在しない。

ルーム作成・参加予約はそれぞれ60秒の期限である。`_expire()` は期限切れ予約を消し、状態が `open` のまま両 slot が空になるとルームを削除する。状態が更新されないため、試合が60秒を超えると次の状態になり得る。

1. Dedicated Server では既存 `sessions[room_id]` が試合中のまま残る。
2. Lobby DB では予約期限が切れ、公開一覧上の `players` が0になる。
3. そのルームに新しい参加予約ができ、Lobby は token を発行する。
4. Dedicated Server の既存セッションは slot が埋まっているため `join_room` を拒否する。

### 影響

デフォルト試合時間は90秒なので、通常の試合でも60秒を超えた時点で、Lobby の表示・予約状態と Dedicated Server の実体がずれる。再接続や一覧からの参加が「予約成功後に接続拒否」になる可能性がある。

### 推奨確認

- ルーム作成から60秒以上経過させ、試合中に `GET /v1/rooms` の `players/status` と Dedicated Server の `sessions` を比較する。
- 試合開始時、終了時、全 peer 切断時に `room_status` を送る責務をどこに置くか仕様化する。
- 予約期限を ENet 接続・試合状態と連動させる。

## BA-02: 同時参加予約の SQLite 競合

- **対象**: `server/lobby/database.py:9,33-45`
- **優先度**: 高
- **確度**: 再現済み

### 事実

`LobbyDatabase` は `check_same_thread=False` の単一 SQLite 接続を FastAPI の複数リクエストから共有している。`reserve()` は `with self.connection:` の中で空 slot の SELECT と UPDATE を行うが、コード上 `BEGIN IMMEDIATE` や排他ロックを開始していない。ファイル先頭の「immediate transaction」という説明と実装が一致していない。

8スレッドから同じ room に同時 `reserve()` を呼ぶ簡易検証では、次の結果を確認した。

- slot 2 の成功が複数回返る
- `sqlite3.InterfaceError: bad parameter or other API misuse`
- `sqlite3.OperationalError: cannot commit - no transaction is active`

### 影響

同時に参加ボタンを押した場合、同じ slot の token が複数発行されたり、500系相当のエラーになったりする可能性がある。後から Dedicated Server に接続した peer は slot 重複で拒否される。

### 推奨確認

- Uvicorn の実ワーカー構成で、同じ room に対する同時 POST を負荷試験する。
- 予約処理を接続単位で分離するか、`BEGIN IMMEDIATE` と適切な再試行を用いる。
- slot 更新条件を SQL の原子操作にし、更新行数を検証する。

## BA-03: 内部状態更新 API の認証不足

- **対象**: `server/lobby/app.py:48-52`、`deploy/Caddyfile:1-3`
- **優先度**: 高
- **確度**: コード上確実

### 事実

`POST /internal/rooms/{room_id}/status` は `status` の値だけを検証し、共有 secret、署名、送信元制限、管理用認証のいずれも確認していない。Caddy は API 全体を外部ドメインへ reverse proxy しているため、`/internal` も同じ公開経路に乗る。

### 影響

room_id を知っている第三者が、任意の room を `closed` にして一覧から隠したり、`open` に戻して予約可能にしたり、`running` と表示させたりできる。Dedicated Server 側の状態通知を実装する場合、この API をそのまま公開するとルーム状態の改ざん点になる。

### 推奨確認

- 本番相当の Caddy 経由で認証なし POST が通ることを確認する。
- Dedicated Server 専用 secret または HMAC、管理ネットワーク限定、もしくは内部ポート分離を導入する。
- `open → running → closed` の遷移制約と送信元の room 所有権も検証する。

## BA-04: ready 未確認の試合開始 RPC

- **対象**: `scripts/network/dedicated_server.gd:83-87`、`scripts/network/match_session.gd:63-75`
- **優先度**: 中
- **確度**: コード上確実

### 事実

`request_match_start` は `any_peer` の reliable RPC として公開され、`session.start()` を直接呼ぶ。`MatchSession.start()` が検証するのは peer 数が2であることと phase が lobby であることだけで、`ready[1]` と `ready[2]` を確認していない。一方、通常の `set_ready()` 経路だけは両者 ready のときに `start()` を呼ぶ。

### 影響

クライアントまたは将来追加される UI が `request_match_start` を呼ぶと、片方または両方が未準備でも試合が始まる。悪意のある peer が RPC を直接送る場合も同じ状態になる。

### 推奨確認

- 2 peer 接続後、ready を送らずに `request_match_start` を送って phase が `match` になることを確認する。
- `start()` 自体を ready 両者必須にするか、未使用 RPC を削除する。

## BA-05: 切断後の result セッションへの再参加

- **対象**: `scripts/network/match_session.gd:19-35`、`scripts/network/dedicated_server.gd:146-155`
- **優先度**: 中
- **確度**: コード上確実

### 事実

`leave()` は peer が切断すると `phase = "result"` にし、残った peer がいる間は Dedicated Server が `sessions` から room を削除しない。しかし `join()` は `phase` を確認せず、空いている slot があれば `result` phase の session にも peer を追加できる。

### 影響

試合終了後または試合中の片方切断後、同じ room と有効な slot token を持つ peer が result session に参加できる。新 peer は新しい試合を開始できず、終了済み snapshot を受け取るだけになる。slot・peer の表示や再接続 UX も不整合になる。

### 推奨確認

- 片方の peer を切断し、残った peer がいる状態で別 peer が空 slot に join できるか確認する。
- `join()` を `phase == "lobby"` のみに制限し、再試合・再接続は専用の状態遷移として扱う。

## 追加観察（今回の時点ではバグ確定にしないもの）

### 入力軌跡の座標・有限値検証

`MatchProtocol.valid_event()` はなぞり点数を512点以下に制限するが、座標の範囲や NaN / Inf 相当の値を検証していない（`scripts/network/match_protocol.gd:41-42`）。`TraceEvaluator` は受信値を距離・対数計算へ渡すため、異常値の RPC に対する採点結果や CPU 使用量を追加確認したい。

### HMAC 比較の定時間性

Dedicated Server の token 検証は `hmac.finish().hex_encode() == parts[1]` と通常比較している（`scripts/network/dedicated_server.gd:168-171`）。現実の攻撃成立性は配置・ネットワーク条件に依存するが、Lobby 側の `hmac.compare_digest` と実装が不一致であるため、共通検証ロジックまたは定時間比較へ統一したい。

## 検証結果

- `godot --headless --path . --script res://tests/network/match_simulation_test.gd`: **成功**（`server-authoritative match simulation tests passed`）。
- `python -m compileall -q server/lobby`: **成功**。
- Lobby の既存 pytest は、グローバル環境に `pytest` がなく実行できなかった。プロジェクト内 `server/lobby/.venv` には FastAPI 等の依存関係があることを確認した。
- Dedicated Server の実起動は、検証環境で UDP 7000 の ENet host 作成に失敗したため、接続を伴う統合テストまでは実施できなかった。
- 既存のユーザー変更・未追跡ファイルは調査対象として保持し、今回の報告書と steering 以外の実装修正は行っていない。

## 対応順の提案

1. BA-02 の予約処理を原子化し、同時参加で壊れないことをテストする。
2. BA-01 の状態通知と期限管理を設計し、試合中の room が誤って再公開されないようにする。
3. BA-03 の内部 API を認証・公開経路の両面で保護する。
4. BA-04、BA-05 の phase/ready ガードをサーバー側の不変条件として追加する。
