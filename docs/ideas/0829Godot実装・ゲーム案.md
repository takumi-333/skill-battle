# スキル対戦ゲーム：Godot実装・ゲーム案

## 1. 最初に作るべき遊べる形

最初の目標は、**1画面・1対1・60〜90秒で完結する対戦**を、3キャラクターで成立させることとする。

- キャラクター: 打鍵者、算術士、詠唱者
- マップ: 遮蔽物を置かない横長の1マップ
- 共通行動: 移動、通常攻撃（または弱い共通スキル）
- 固有行動: 画面上の課題を成功させると、キャラクター固有の技が発動する
- 勝利条件: 相手のHPを0にする。時間切れは残HPの多い側が勝利

いきなり育成・ランク・複数マップを同時に作らず、まず「課題入力中の隙」と「それを狙う相手」の読み合いが面白いかを確かめる。この対戦コアが成立してから、育成やマッチングを足す。

## 2. 1試合の流れ案

1. マッチ成立後、両者がキャラクターとビルドを確定する。
2. 3秒のカウントダウン後に開始する。
3. プレイヤーは移動で位置を取り、任意のタイミングで固有スキルの課題を開始する。
4. 課題の成績に応じて、技の威力・発生・効果量が決まる。
5. HPが0になるか制限時間が終わるとリザルトへ進む。

### 課題中のルール案

- 課題を始めると、キャラクターは「集中状態」になる。集中状態であることは、キャラクターのエフェクトで相手にも分かるようにする。
- 集中状態では移動速度が激減し、通常攻撃はできない。
- 集中状態には課題中断用のゲージを持たせる。被ダメージがゲージの値に達すると課題が中断される。
- 中断ゲージは両プレイヤーに表示する。攻撃側は「あとどれだけで中断させられるか」を判断でき、集中側は課題を続けるか中止するかを判断できる。

この可視化により、課題中は単なる無防備な時間ではなく、「大技を完成させるまで耐えられるか」と「相手の集中を崩し切れるか」を争う時間にする。

## 3. 3キャラクターの試作ゲーム案

| キャラクター | 課題 | 小技 | 大技 | 対戦で作りたい読み合い |
| --- | --- | --- | --- | --- |
| 打鍵者 | 表示された単語・短文を入力する | 短い単語で前方へ速い弾を放つ | 長文成功で高威力・長射程の貫通弾 | 距離を取って大技を詠むか、短い入力で相手を追い払うか |
| 算術士 | 四則演算を解く | 正解すると自分を短時間強化、または小さな妨害弾 | 難しい問題の正解で相手の行動を制限する設置技 | どの効果の問題を解くかを状況で選ぶ |
| 詠唱者 | 表示された図形をマウスでなぞる | 短い線をなぞって近距離の範囲攻撃 | 円・星などを正確になぞって持続する魔法陣を設置 | 相手の逃げ道を魔法陣で狭め、次の行動を誘導する |

最初は各キャラクターを「小技1・大技1」に限定する。技の数よりも、課題の気持ちよさと対戦中に見える駆け引きを優先する。

## 4. 課題の成績を技に変換する案

課題の成功・失敗だけでなく、速度と正確性を連続的に技の性能へ反映する。

```text
集中状態になる → 入力受付・中断判定 → 成績を算出 → 技の性能を決定 → 発動演出 → 攻撃判定
```

- 成績: 正確性、入力時間、課題難度を使って 0〜100 点に正規化する。
- 小技: 低い点数でも最低限発動し、高得点ほど速さや威力が伸びる。
- 大技: 合格点を満たしたときだけ発動し、高得点で追加効果を付ける。
- 失敗: 不発だけにせず、短い硬直やクールダウンを発生させる。ただし初心者が何もできなくならない程度に抑える。

成績の計算式はキャラクターごとにばらばらにせず、共通のスコア形式にする。バランス調整とリザルト表示が扱いやすくなる。

## 5. Godotの構成案

Godot 4 を前提に、ゲーム世界・課題UI・対戦状態を分ける。

```text
Main
├─ Lobby                         # ルーム作成・参加、キャラクター選択
├─ Match                         # 1試合の親シーン
│  ├─ World (Node2D)             # マップ、キャラクター、弾、当たり判定
│  ├─ MatchHud (CanvasLayer)     # HP、タイマー、集中状態・中断ゲージ、スコア表示
│  └─ ChallengeLayer (CanvasLayer)# タイピング・計算・なぞりの課題UI
└─ Result                        # 勝敗と課題成績
```

### シーンとスクリプトの役割

| 要素 | Godotでの候補 | 役割 |
| --- | --- | --- |
| キャラクター | `CharacterBody2D` | 移動、状態（通常・集中・硬直）、HP・中断ゲージ、被弾処理 |
| 技 | `Node2D` / `Area2D` | 弾、範囲攻撃、設置物、当たり判定 |
| キャラクター定義 | `Resource` | 見た目、初期スキル、成長可能な項目 |
| スキル定義 | `Resource` | 課題種別、難度、クールダウン、スコアごとの効果 |
| 課題UI | `Control` | 入力受付、進捗、成功・失敗の表示 |
| 試合進行 | `MatchController` | 開始・終了、制限時間、勝敗、スポーン管理 |

キャラクター固有の処理を1つの巨大なスクリプトに書かず、`CharacterDefinition` と `SkillDefinition` のデータを差し替えて追加できる形にする。将来のキャラクター追加で、共通の対戦基盤を壊しにくくなる。

## 6. 課題UIの実装イメージ

`ChallengeLayer` は、共通の開始・中断・採点の窓口を持ち、課題ごとのUIを差し替える。中断ゲージ自体は対戦状況として `MatchHud` に表示し、両者が確認できるようにする。

```text
ChallengeLayer
├─ TypingChallenge      # LineEdit と目標テキスト
├─ ArithmeticChallenge  # 問題文、選択肢または数値入力
└─ TracingChallenge     # 描画用Control、軌跡のサンプル点、目標図形
```

- 打鍵者: `LineEdit` を使い、入力文字列・誤字数・経過時間から採点する。
- 算術士: 最初は選択式または1〜2桁の数値入力に絞る。問題生成には乱数シードを使い、同じ問題を再現できるようにする。
- 詠唱者: マウス／タッチの座標を一定間隔で記録し、目標図形を同じ数の点に正規化して距離を比較する。最初から複雑な手書き認識は行わない。

UIは画面中央を大きく覆いすぎず、対戦中の相手と弾が見える大きさにする。課題に集中しつつも、相手の接近に気付けることがこのゲームの緊張感になる。

## 7. オンライン対戦の実装方針

最初のオンライン方式は、Godot の高レベルマルチプレイヤーAPIと `ENetMultiplayerPeer` を使うホスト方式を候補にする。1人がホストになり、ホストが試合の正しい状態を管理する。

```text
クライアントの操作入力
        ↓ RPC
ホストが移動・課題・攻撃を判定
        ↓ 状態同期
両クライアントが画面に表示
```

### ホスト側で判定するもの

- キャラクターの位置、HP、クールダウン、試合時間
- 集中状態、中断ゲージの値、課題を開始・中断できるか
- タイピング文字列、計算の回答、なぞり軌跡の採点
- スキルの発動可否と攻撃の命中

入力結果だけをクライアントから送ると、改造で満点を送れてしまう。課題の開始時刻と乱数シードをホストが決め、クライアントからは入力内容を送り、ホストで再計算する方針にする。

ただしホストプレイヤー自身の不正や回線切断には弱い。対戦が成立した後で、ランクマッチだけは専用サーバー化するか、リプレイ検証・不正検知を追加するかを判断する。

### 実装の順序

1. 同一PCの2人対戦（またはボット相手）で、3種の課題と攻撃判定を検証する。
2. `MatchController` の操作入力を `PlayerCommand` としてまとめ、ローカル入力とネットワーク入力を同じ経路で扱えるようにする。
3. ENetによるルーム作成・参加、位置と技の同期を加える。
4. 遅延・切断・再接続時の扱いを決め、通信環境で試す。

この順番でも、2 の時点でネットワークを意識した入力の境界を作るため、後から全面的に作り直すことを避けられる。

## 8. 育成・ビルドのデータ案

キャラクターレベルは「使い込んだ記録」と「選択肢の解放」を担い、単純なHPや攻撃力の恒久上昇には寄せない。

```text
PlayerProfile
└─ character_progress[character_id]
   ├─ level
   ├─ experience
   ├─ unlocked_skill_ids
   └─ allocated_skill_points
```

- レベルアップでスキルポイント、スキル枠、見た目報酬などを解放する。
- 対戦前にビルドを選び、スキルポイントを割り振る。
- リセットはいつでも無償で行い、`allocated_skill_points` を未使用ポイントへ戻す。
- プロトタイプでは `ConfigFile` または JSON にローカル保存する。オンラインの正式サービスでは、プロフィールをサーバー側で保存する。

ランクマッチは、全プレイヤーが同じだけのポイントを使える「対戦用ビルド」にする案が有力である。育成差による理不尽さを避けながら、ビルドを考える楽しさは残せる。

## 9. 最初の実装マイルストーン案

| 段階 | 到達点 | 確認したいこと |
| --- | --- | --- |
| 0. 操作試作 | 画面内を2体が移動し、当たり判定がある | 移動・攻撃の手触り |
| 1. 課題試作 | 3種類の課題でそれぞれ1技を発動できる | 入力そのものが気持ちよいか |
| 2. 対戦試作 | 小技・大技、集中エフェクト・中断ゲージ・中断、勝敗までを実装する | 読み合いが生まれるか |
| 3. ローカル完成形 | 3キャラクター・リザルト・簡易ビルドを入れる | 何度も対戦したくなるか |
| 4. オンライン試作 | ルーム作成・参加・ホスト判定で1対1できる | 遅延下でも公平に遊べるか |
| 5. 育成試作 | キャラ別経験値、割り振り、即時リセットを入れる | 継続して遊ぶ動機になるか |
