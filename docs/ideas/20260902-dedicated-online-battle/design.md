# 設計書

## アーキテクチャ概要

PC版クライアント、ロビーAPI、Godot専用対戦サーバーを分離する。VMには小規模試遊向けにロビーAPIと専用サーバーを同居させるが、通信経路とプロセスは分ける。クライアントはロビーAPIにHTTPSで問い合わせ、試合中だけ専用サーバーへENet/UDPで接続する。

```text
PCクライアント A ─HTTPS─┐
                           ├─ Lobby API (TCP 443) ─ SQLite
PCクライアント B ─HTTPS─┘          │
                                     │ ルーム作成・参加予約
PCクライアント A ──────── UDP 7000 ─┤
                                     └─ Godot Dedicated Server
PCクライアント B ──────── UDP 7000 ─   └─ MatchSession × 最大10
```

### 固定する初期値

| 項目 | 初期値 | 理由 |
| --- | --- | --- |
| VM | OCI Ampere A1、2 OCPU、12GB RAM | Always Free上限を専用サーバーに集中させる。 |
| 対戦サーバー | 1プロセス、UDP 7000 | ENetを継続する。 |
| ルーム定員 | 2人 | 初期対戦仕様に合わせる。 |
| 同時ルーム上限 | 10 | まず20人で計測するための安全な開始値。 |
| シミュレーション | 60 tick/秒 | 現行のリアルタイム操作に合わせ、サーバーで固定する。 |
| 状態送信 | 20回/秒、unreliable | 現行の `STATE_SYNC_INTERVAL = 0.05` を踏襲する。 |
| ロビーAPI | Python 3 + FastAPI + SQLite | 小規模で導入・バックアップが単純であり、ゲームプロセスと障害を分離できる。 |

## コンポーネント設計

## プログラムの切り分け方針

専用サーバーは、現在の`match_prototype.gd`を複製してUI部分を削ったものにはしない。現行ファイルには描画、入力、画面遷移、RPC、試合状態更新、スキル演出が混在しているため、試合のルールを共有層へ切り出し、その共有層をサーバーとクライアントが異なる形で利用する。

### AI開発を前提にした保守性・拡張性の原則

このプロジェクトでは人間がソースコードを細部まで読むことよりも、AIが既存の責務と変更範囲を正確に把握し、安全に実装・検証できることを重視する。そのため、一般的な設計上の慣習を目的化せず、次の機械的なルールを優先する。

- 1ファイル1責務を基本とし、1ファイルが大きくなったら「状態」「ルール」「通信」「表示」「設定」の単位で分割する。
- 依存方向を`表示 → 通信 → 共有ドメイン`に固定し、共有ドメインからUI・入力・ネットワークを参照しない。
- クラスや関数の境界では、入力型、出力型、状態を変更するかどうか、失敗時の結果を明記する。暗黙のDictionaryキーやグローバル状態を増やさない。
- 試合状態、入力メッセージ、スナップショット、Lobby APIのJSONは専用のデータ型またはスキーマを正本にする。
- キャラクター、スキル、採点係数、通信間隔など、調整が想定される値は処理コードから分離し、設定データとして管理する。
- 追加キャラクターや追加スキルは、既存のサーバー本体を大きく変更せず、ルール・設定・登録表を追加して実装できる構造を目指す。
- 変更ごとに共有ロジックのユニットテスト、通信境界のテスト、必要な実画面確認を対応付ける。テストが責務の境界を示す設計資料になるようにする。
- 便利そうな共通化を先行しない。複数の実例で同じ契約が確認できた箇所だけを共通化し、過度な抽象層を作らない。
- AIが作業を再開できるよう、各モジュールの目的、公開API、参照してよい依存先、検証コマンドを近接ドキュメントまたはファイル冒頭に残す。

可読性のための分割ではなく、変更時にAIが「どこを変更し、どこを検証すべきか」を局所化するための分割とする。ゲームルールの変更がUIや通信実装の意図しない変更を要求しないことを、保守性の主要な判定基準にする。

```text
共有ドメイン層（UI・Input・RPCに依存しない）
  ├─ MatchState / PlayerState / RoomState
  ├─ MatchInput / ChallengeAnswer などの入力データ
  ├─ MatchSimulation              試合状態の更新・勝敗判定
  ├─ CombatRules                  移動・攻撃・当たり判定・ダメージ
  ├─ ChallengeRules               課題生成・回答検証・採点
  └─ GameBalance                  キャラクター・スキル・定数
          ↑                         ↑
サーバー層                         クライアント層
  ├─ DedicatedServer               ├─ DedicatedClientConnection
  ├─ MatchSession × 複数            ├─ InputCapture
  ├─ ENet RPC受信・入力検証          ├─ SnapshotInterpolator
  ├─ 60Hz tick                      ├─ ChallengeView / HUD
  └─ 状態スナップショット送信        └─ 演出・画面表示

Lobby API（Godotとは別プロセス）
  ├─ ルーム作成・一覧・参加予約
  ├─ 短命トークン発行・検証
  └─ 専用サーバーとの開始・終了通知
```

### 共有ドメイン層

共有層は`RefCounted`またはデータ保持用クラスを中心にし、`Control`、`CanvasItem`、`Input`、`draw_*`、画面シーン、`multiplayer`への直接依存を持たせない。ここでは「入力を受け取った結果、次の状態がどうなるか」だけを扱う。

- `MatchState`はプレイヤー位置、HP、課題状態、攻撃・飛翔体・ゾーン、残り時間、勝敗を保持する。
- `MatchSimulation.step(delta, inputs)`は、検証済み入力を受けて60Hz単位で状態を更新する。クライアントから呼び出して正解を決める用途には使わず、主判定はサーバーだけで行う。
- `CombatRules`と`ChallengeRules`は、移動可能範囲、攻撃命中、ダメージ、課題採点、スキル成立条件を担当する。
- 共有層のテストではネットワークや画面を起動せず、同じ初期状態と入力列から同じ結果になることを確認する。

### 専用サーバー側

サーバーのエントリーポイントは`scenes/server_main.tscn`と`scripts/network/dedicated_server.gd`に固定する。ヘッドレス起動時には画面シーンやプレイヤー用UIを生成せず、ENetの受信、入力検証、ルーム管理、シミュレーション更新、状態送信だけを行う。

- `DedicatedServer`はENetの待受を一度だけ開始し、接続中のpeerを認証する。
- `MatchSession`は1ルーム分の`MatchState`、2つのslot、peer ID、入力キュー、tick時刻、切断状態を保持する。
- `DedicatedServer`は`room_id`から`MatchSession`を引き、受信したRPCを該当ルームへ渡す。ルームごとにENet peerを作らない。
- クライアントからは位置、HP、スコア、勝敗結果を受け取らない。受け付けるのは、割り当てslotに紐付いた移動入力、攻撃要求、課題入力、準備・再戦要求だけとする。
- 入力はサーバー側で型、値の範囲、送信頻度、連番、slot、現在の試合状態を検証してから`MatchSimulation`へ渡す。
- 60Hzでシミュレーションを進め、20Hzで同一ルームのクライアントだけへスナップショットを送る。スナップショットにはクライアントが表示するための状態だけを含める。
- サーバー側に課題UIやスキル演出を実装しない。課題の正解・採点などのルールは共有層で実行し、表示はクライアント側で行う。

### クライアント側

クライアントは入力と表示を担当し、試合結果の権威にはしない。現在の`match_prototype.gd`から、UI生成・`Input`参照・演出・スナップショット表示を段階的にクライアント側へ残し、試合判定を共有層とサーバー側へ移す。

- `DedicatedClientConnection`がLobby APIから取得した接続先・room ID・参加トークンを使ってENetへ接続する。
- `InputCapture`がキーボード、マウス、ペン、課題入力を入力データへ変換し、サーバーへ送る。入力値の最終検証はサーバーで行う。
- `SnapshotInterpolator`がサーバーから届いた状態を補間し、プレイヤーや飛翔体を描画する。
- 課題UIは入力軌跡や回答を表示するが、成功・失敗・得点を確定せず、サーバーから返った結果を表示する。
- ローカル練習モードは専用サーバーへ接続せず、既存のローカル実装を当面維持する。オンラインモードだけを新しい入力送信・スナップショット表示経路へ切り替える。

### Lobby APIとの境界

Lobby APIはFastAPIの別プロセスとして実装し、Godotの試合シミュレーションを直接呼び出さない。Lobby APIは「誰がどのroomへ参加できるか」を管理し、試合中の位置、攻撃、課題、勝敗はDedicated Serverが管理する。

- クライアント ↔ Lobby API: HTTPS（ローカルではHTTP）でルーム情報、参加トークン、接続先を取得する。
- クライアント ↔ Dedicated Server: ENet/UDPで入力と試合状態を交換する。
- Dedicated Server → Lobby API: 内部APIで試合開始、切断、終了を通知する。
- Lobby APIのSQLite状態とDedicated Serverの進行中`MatchState`は別管理とし、サーバー再起動時に試合状態を復元しない。

### 分離の実装順序

一度に全面改修せず、次の順で切り出す。

1. 現行コードから課題採点、当たり判定、移動制限、ダメージ、勝敗判定を副作用の少ない共有クラスへ移す。
2. 共有クラスを使う`MatchSimulation`を作り、既存のローカル対戦で結果が変わらないことを確認する。
3. `DedicatedServer`と`MatchSession`を追加し、クライアント1個から入力を受けて状態を返す。
4. クライアント2個を同じサーバーへ接続し、ルーム単位の状態分離を確認する。
5. 最後にLobby APIとルーム一覧を接続し、オンライン通常導線へ切り替える。

### 1. `MatchSimulation` と `MatchSession`

**責務**:

- `MatchState` を保持し、移動、攻撃、課題、ダメージ、勝敗をtickごとに更新する。
- ENet peer ID と `{room_id, player_slot}` を対応付け、ルーム内の2人だけへ結果を送る。
- 切断、入力タイムアウト、満室、試合終了を処理してロビーへイベントを通知する。

**実装の要点**:

- `match_prototype.gd` に混在している `update_player`、攻撃・課題・勝敗の状態更新を、UIに依存しない `scripts/network/match_simulation.gd` へ移す。`Input`、`Control`、`draw_*` はここに置かない。
- `scripts/network/dedicated_server.gd` はENetサーバーを一度だけ開始し、RPCを受けてroom IDから `MatchSession` を引く。各ルームで別の `ENetMultiplayerPeer` を作らない。
- 参加直後にトークンを含む `join_room` RPCを送る。認証済みで空席のときだけslotを確定する。サーバーが割り当てるslot以外の入力は破棄する。
- 移動は正規化して上限速度を越えないようにし、アクションには連番を付けて同一入力の連打・再送を防ぐ。課題回答、ロビー準備、試合結果はreliable、定期入力と状態スナップショットはunreliableにする。

### 2. PCクライアントのネットワーク表示

**責務**:

- ロビーAPIからルーム一覧・参加トークン・接続先を受け取る。
- 自身の入力を送信し、サーバースナップショットを補間して表示する。
- 作成、参加、満室、接続失敗、切断、試合終了をUIで案内する。

**実装の要点**:

- 現行の `start_host()` はデバッグ用ローカルホストとして残し、通常のオンライン画面では呼ばない。新たに `DedicatedClientConnection` を用意して、ロビーの接続情報で `create_client()` を実行する。
- 現在はホストのローカル入力を `MatchPrototype` が直接試合処理しているため、オンライン時は両プレイヤーを同じ `send_input` 経路に統一する。
- `receive_network_state` の補間表示は維持しつつ、状態の作成・判定をクライアントから除く。クライアント独自の勝敗・採点確定を禁止する。
- HTTP通信はGodotの `HTTPRequest` を使い、API失敗時は再試行可能なエラー文と「一覧へ戻る」を表示する。

### 3. Lobby API

**責務**:

- ルームの作成、公開一覧、参加予約、状態更新、期限切れ削除を行う。
- 専用サーバーからのルーム開始・終了通知を受け、表示上の人数と状態を整合させる。
- 参加者用の短命・一回限りトークンを発行する。

**API初期案**:

| メソッド | パス | 用途 |
| --- | --- | --- |
| `POST` | `/v1/rooms` | ルーム名を受け、`room_id` と作成者用参加トークンを返す。 |
| `GET` | `/v1/rooms` | `open` のルーム名・人数・作成時刻を返す。秘密値は返さない。 |
| `POST` | `/v1/rooms/{room_id}/join` | 空席を原子的に予約し、参加トークンとUDP接続先を返す。 |
| `POST` | `/v1/internal/rooms/{room_id}/event` | 専用サーバーのみが開始・切断・終了を通知する。 |
| `GET` | `/healthz` | systemd監視と更新確認用。 |

**実装の要点**:

- SQLiteのトランザクションで定員確認と予約を一度に行う。予約は60秒で失効させ、接続されなければ空席へ戻す。
- トークンは署名付き、10分有効、`room_id`・割当slot・用途を含める。署名鍵は `/etc/skill-battle/server.env` にだけ置く。
- ルーム一覧はIPアドレスやトークンを返さない。ルーム名は文字数・制御文字を検証し、APIにはIPごとのレート制限を設定する。

## データフロー

### ルーム作成から試合開始

```text
1. クライアントAは POST /v1/rooms を呼び、room_id と作成者トークンを得る。
2. クライアントAは UDP 7000へ接続し、join_room(room_id, token) を送る。
3. クライアントBは GET /v1/rooms で一覧を取得し、POST /join で空席を予約する。
4. クライアントBも join_room を送る。専用サーバーはトークンを検証してslot 2へ割り当てる。
5. 両者がキャラクター選択・準備完了を送る。MatchSessionが60Hzで試合を開始する。
6. 各クライアントは入力を送信し、サーバーは20Hzの状態を当該ルームだけへ送信する。
7. 試合終了・切断時、サーバーはルームをclosedにしてLobby APIへ通知する。
```

## ローカル開発・検証構成

VM配備前の標準的な開発構成は、Windows PC上のWSL2をLinuxサーバー環境として利用する。Windows側のGodotクライアントとWSL2側のサーバープロセスを分離し、専用サーバーがクライアントの描画・入力UIに依存していないことを早期に確認する。

```text
Windows PC
  ├─ Godot Client A
  ├─ Godot Client B
  └─ WSL2 (Linux)
       ├─ Godot Dedicated Server : UDP 7000
       └─ FastAPI Lobby API       : TCP 8000
```

### ローカル接続の方針

- ローカル開発ではLobby APIをHTTP `127.0.0.1:8000`、対戦サーバーをUDP `127.0.0.1:7000`で起動する。必要に応じてGodotクライアントからは`localhost`を接続先に指定する。
- サーバー、Lobby API、クライアントは別プロセスで起動する。クライアントを2個起動して、作成者と参加者の両方を再現する。
- WSL2のネットワーク方式に依存する接続不具合を避けるため、サーバーのbindアドレス、Windowsファイアウォール、WSL2のポート転送設定を起動手順に明記する。まず同一PC内の接続を対象とし、LAN内の別PC接続は追加検証とする。
- ローカルではTLS終端のCaddyを必須にしない。HTTPS、公開証明書、OCIの受信規則はVM検証で確認する。

### ビルド対象の切り分け

- WSL2では開発PCのCPUアーキテクチャに合わせたLinux版Dedicated Serverを使用する。Windowsクライアントとは別のLinux向けエクスポート成果物を作る。
- OCIのAmpere VM向けにはLinux ARM64版を別途作成する。WSL2で試合ロジックとプロトコルを検証できても、ARM64での起動確認はOCI VMで行う。

## VM構築・配備設計

VM構築は、WSL2でローカル統合検証が完了した後に行う。VMではローカルで確認済みの成果物を配備し、外部ネットワーク、TLS、公開ポート、systemd、自動再起動、ARM64実行環境を検証する。

1. OCIでホームリージョンを選び、Always Free対応のUbuntu Arm VMを2 OCPU・12GBで作成する。ブート・ブロックボリューム合計を200GB以内にする。
2. VCNのセキュリティリスト／Network Security Groupで、UDP 7000、TCP 443、管理元固定IPからのTCP 22だけを受信許可する。OSのUFWにも同じ規則を設定する。
3. 管理用の非rootユーザーとSSH鍵を作り、パスワードSSHとrootログインを無効化する。OSの自動セキュリティ更新を有効にする。
4. CIまたは管理PCでGodotのLinux Dedicated Server用ビルドを作成し、成果物をVMの `/opt/skill-battle/server/releases/<version>/` にアップロードする。リポジトリ全体・開発用鍵は置かない。
5. `/opt/skill-battle/lobby/` にFastAPIをvenvで配置し、SQLite DBは `/var/lib/skill-battle/lobby.db` に置く。DBは毎日バックアップする。
6. Caddyを443で稼働させ、APIだけをリバースプロキシする。ドメインを使わない試遊では自己署名証明書の指紋をクライアントへ安全に配布する。一般公開前は独自ドメインとLet's Encryptを必須にする。
7. `skill-battle-server.service` と `skill-battle-lobby.service` を `Restart=on-failure` で有効化し、`journalctl` と `/healthz` で確認する。

## エラーハンドリング戦略

- API不達: 接続情報を生成せず、再試行・一覧に戻る操作を表示する。
- UDP接続失敗: 10秒でタイムアウトし、予約を明示的に取り消すか自然失効させる。
- 無効／期限切れトークン: slotを割り当てず、クライアントを切断してロビー再参加へ戻す。
- 切断: 試合中は即時敗北扱い、待機中はroomをopenへ戻すか、作成者切断ならclosedにする。
- サーバー再起動: 進行中roomを復元しない。API側の予約を失効し、クライアントに「サーバー再起動」を表示する。

## テスト戦略

### ユニットテスト

- `MatchSimulation` の移動上限、攻撃命中、集中中断、課題採点、勝敗、入力連番の検証。
- トークンの署名、有効期限、room/slot不一致、SQLiteの満室競合、予約期限切れの検証。

### 統合テスト

- ローカルで専用サーバー1つとクライアント2つを起動し、作成・参加・90秒試合・切断を確認する。
- VMで異なるネットワークのPC 2台から、一覧→参加→試合→結果へ進めることを確認する。
- 疑似クライアント20人（10ルーム）で、CPU、メモリ、tick遅延、パケット損失、各ルームの独立性を測る。

## 依存ライブラリ

Godot側は既存のENet高レベルマルチプレイヤーAPIを継続して使う。ロビーAPIにはPython 3、FastAPI、Uvicorn、SQLite（標準ライブラリ）を追加する。CaddyはVMのTLS終端にのみ使用する。

## 実装の順序

1. 現行試合ロジックをUIから分離し、ローカル専用サーバー＋クライアント2つで同じ試合を再現する。
2. 専用サーバーに複数 `MatchSession` と参加トークン検証を実装し、クライアントの通常導線を切り替える。
3. ロビーAPI、ルーム一覧UI、トークン予約、切断処理を実装する。
4. Linux用成果物、OCI構築手順、systemd、監視・ログを追加する。
5. VM上の外部接続・負荷試験を実施し、上限値を実測で調整する。

## セキュリティ考慮事項

- クライアントが送る位置、HP、スコア、勝敗を信頼しない。
- UDPはTLSで暗号化されないため、ログイン情報や恒久的な個人情報をENet RPCに載せない。初期は匿名の短命参加トークンのみを使う。
- APIはHTTPS、管理SSHは鍵認証と送信元IP制限、秘密値はVM上の権限を絞った環境ファイルに置く。
- RPC入力の型、長さ、頻度、プレイヤーslotを検証する。なぞり座標数など可変長入力には上限を設ける。

## パフォーマンス考慮事項

- ルームごとの状態を分離し、同一roomのスナップショットだけを配信する。
- 入力は小さい構造体、状態は20Hzの差分または必要最小限のスナップショットとし、描画やUI処理をサーバーに含めない。
- 10ルームから計測を始め、CPUが80%を継続して超える、tick遅延、250ms超の同期遅延が出る場合は定員を下げる。無料枠での実用上限は実測値を採用する。

## 将来の拡張性

ルーム管理と試合シミュレーションを分離するため、将来はLobby APIを別VM／DBへ移し、専用サーバーを複数台に増やせる。Web版は現行ENetを流用せず、WebRTCまたはWebSocket専用の接続層を別途設計する。
