# 要求内容

## 概要

現在のプレイヤーPCがホストになる1対1オンライン試作を、インターネット上のLinux VMで動く専用対戦サーバー方式へ移行する。PC版クライアントはルーム一覧から公開ルームを選び、IPアドレスの共有や家庭用ルーターのポート開放なしで対戦できるようにする。

## 背景

現状の `scripts/match_prototype.gd` は、ルーム作成者がENetサーバーを開始し、参加者が `IP:ポート` を直接入力する方式である。試合判定はホスト側で行えているが、ホストがプレイヤーでもあり、公開ルーム一覧・接続先の解決・複数ルーム管理・専用VMへの配備がない。

## 実装対象の機能

### 1. 専用サーバー権威の試合処理

- Godotの描画・UI・ローカル入力処理から、試合ルールと状態更新を分離する。
- Linuxのヘッドレス／Dedicated Serverエクスポートで、プレイヤーを持たない対戦サーバーを起動する。
- サーバーはルームごとに2席を管理し、位置、攻撃、HP、課題、採点、勝敗を唯一の正として判定する。
- クライアントは入力と課題回答だけを送り、サーバースナップショットを表示する。

### 2. 公開ルームのロビー

- ルーム作成、一覧取得、参加予約、満室・切断・試合終了時の状態更新を行うHTTP APIを追加する。
- クライアントのオンライン画面から、ルーム名を入力して作成し、一覧を更新して選んだルームへ参加できるようにする。
- ロビーAPIは、予約済みプレイヤーだけが対戦サーバーの該当ルームに入れる短命トークンを発行する。

### 3. Oracle Cloud Always Free上の配備と運用

- 無料枠内のArm VMを1台用意し、対戦サーバー、ロビーAPI、SQLiteデータを同居させる。
- UDP 7000（対戦）とTCP 443（ロビーAPI）だけを公開し、SSHは管理者のIPアドレスに制限する。
- systemdで両プロセスを常駐・再起動させ、ログ、バックアップ、更新、停止時の切断通知を運用できるようにする。

## 受け入れ条件

### 専用サーバー対戦

- [ ] 専用サーバーは画面を作らず、クライアント2人をプレイヤー1・2として収容できる。
- [ ] クライアントから送った入力や課題回答は、サーバー側で検証され、サーバーの判定結果だけが両者へ同期される。
- [ ] 同一プロセスで少なくとも10ルーム（20人）を同時に扱い、1室の切断や終了が他室へ影響しない。
- [ ] クライアントまたはサーバーが切断した場合、該当ルームを終了し、両クライアントへ分かる状態を表示する。

### ロビーと接続

- [ ] クライアントは公開ルームを一覧表示し、作成・参加できる。
- [ ] プレイヤーはサーバーIPの入力や自宅ルーターの設定をせずに、ロビーが返す接続情報で入室できる。
- [ ] 満室、期限切れ、無効トークン、対戦サーバー障害を、誤った入室やクラッシュなしに処理する。

### VMと運用

- [ ] Always Free対象リソースの範囲内で、VM上から外部ネットワークのPC 2台が対戦できる。
- [ ] 再起動後もサービスが自動起動し、ログから接続・切断・エラーを確認できる。
- [ ] 既定の通信ポート以外は公開せず、秘密鍵・トークン秘密値をリポジトリへ保存しない。

## 成功指標

- 離れたネットワークのPC 2台が、公開ルームを作成して90秒の試合を完走できる。
- 初期の負荷試験で、10同時ルーム時にサーバーのCPU使用率が継続的に80%未満、メモリ使用量が8GB未満、状態同期の遅延が250ms未満である。

## スコープ外

以下はこのフェーズでは実装しません:

- アカウント登録、恒久的なフレンド、ランクマッチ、自動マッチング、観戦、再接続。
- ブラウザ版（ENet/UDPではなくWebRTCまたはWebSocket設計が必要）。
- 複数VMへの自動スケール、DDoS対策サービス、購入済みドメイン。
- 不正クライアントを完全に防ぐ対策。サーバー権威と入力検証までを対象とする。
