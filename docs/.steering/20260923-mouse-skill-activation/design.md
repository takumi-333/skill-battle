# 設計書

## アーキテクチャ概要

HUD枠は固定のシーン部品として保持し、`HudSkillDiamondWidget` に入力・反応表示だけを追加する。ゲーム状態の変更は `MatchPrototype` に集約し、ウィジェットはクリック要求のシグナルを発行するだけにする。

```text
キー入力 / HUDクリック
        ↓
MatchPrototype.request_skill_activation(slot)
        ├─ local / host: 既存の発動関数
        └─ client: 次フレームの既存ネットワーク入力に一度だけ合成
                         ↓
                   Dedicated Server / 従来ホスト
```

## コンポーネント設計

### 1. `HudSkillDiamondWidget`

**責務**:

- 左クリック、ホバー、押下を検出してスロット番号の発動要求を通知する。
- クールダウンや行動不能状態に応じて、入力可否と見た目を更新する。

**実装の要点**:

- 子の背景・アイコン・フレームはマウスを透過し、ルート部品だけが入力を受ける。
- マウスホバーはキーボードフォーカスを取得しない。課題入力欄のフォーカスを奪わない。
- ホバー時は軽い拡大と明度・枠の強調、押下時は縮小を行う。非活性時はマウス入力を無視する。

### 2. `MatchPrototype` の発動要求窓口

**責務**:

- スロット番号を通常攻撃・小技・大技・スキル3へ対応付ける。
- 実行可能なフェーズとローカル操作対象を確認する。
- クライアントでクリック要求を単発パルスとして既存の入力送信に合成する。

**実装の要点**:

- Dedicated Server接続時は既存の `send_event` を使う。
- 従来のクライアント同期では、クリックを1フレームの入力値として送る。
- 課題中の要求を保留せず破棄して、課題終了後の意図しない発動を防ぐ。

## データフロー

### HUDクリック

1. 発動可能なHUD枠が左クリックの完了を受ける。
2. ウィジェットがスロット番号をシグナルで通知する。
3. `MatchPrototype` がローカル発動またはネットワーク要求へ変換する。
4. 状態同期によりクールダウン・非活性表示が更新される。

## テスト戦略

- ウィジェットの入力可否とホバー状態をスクリプトテストで確認する。
- ローカル対戦でキー・クリック両方の各スロットが発動できることを確認する。
- 課題中、クールダウン中、観戦中にクリックが発動しないことを確認する。
- headless起動でシーン・スクリプトのエラーがないことを確認する。

## 実装の順序

1. ウィジェットにクリック・ホバー・非活性表示を追加する。
2. 発動要求の共通窓口とクライアント用単発要求を追加する。
3. HUD接続と可否更新を追加する。
4. テストとGodot起動で確認する。
