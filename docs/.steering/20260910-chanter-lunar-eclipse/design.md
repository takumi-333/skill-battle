# 設計書

## アーキテクチャ概要

ゲーム結果に影響する月蝕の状態・当たり判定・移動制限は `MatchSimulation` が所有し、`MatchPrototype` は同じ状態をローカル対戦で更新・描画する。ネットワークでは既存スナップショットに月蝕演出配列を含め、クライアント描画は同期済み状態だけを使用する。

```text
スキル3選択（月蝕）
  -> challenge_trace（星）
  -> MatchSimulation / MatchPrototype: lunar_eclipses を生成
       -> ブラックホール吸引・発動者ロック・レーザー命中
       -> snapshot
       -> MatchPrototype: 描画
```

## コンポーネント設計

### 1. MatchSimulation

**責務**:
- 月蝕の開始時に固定した位置・向きとブラックホール中心を保存する。
- 吸引、レーザー命中、時間切れ、発動者の行動制限をサーバー権威で処理する。

**実装の要点**:
- 演出状態は `lunar_eclipses` 配列に `presentation_id` を含めて保持する。
- ブラックホール中心は前方へ射線を伸ばし、ステージ境界との最初の交点までに制限する。
- レーザーの当たり判定は線分と相手の楕円ヒットボックスの重なりで判定する。

### 2. MatchPrototype

**責務**:
- ローカル対戦で同じ月蝕ルールを適用する。
- ローカルおよび同期スナップショットの月蝕演出を描画する。
- スキル候補選択・HUDへ月蝕アイコンを割り当てる。

**実装の要点**:
- 固定時間の描画は `lunar_eclipses` の経過時間から算出し、専用ノードを増やさない。
- 既存の `selected_skills[2]` に月蝕を新しい候補番号で割り当て、ロードアウトの変換を両モードで一致させる。

### 3. 自動テスト

**責務**:
- 候補選択、星形課題、固定位置・向き、吸引、レーザー3ヒット、クールダウンを検証する。

## データフロー

### 月蝕の発動

```text
1. 月蝕選択中の詠唱者が skill3 を開始する。
2. 星形軌跡を45点以上で提出する。
3. 固定位置・向きとブラックホール中心を含む月蝕状態を作成する。
4. 0.1秒ごとに相手を吸引し、1.0 / 1.5 / 2.0秒にレーザー命中を判定する。
5. 2.5秒後に状態を破棄し、発動者の行動制限を解除する。
```

## エラーハンドリング戦略

- ステージ境界計算に有効な前方ベクトルがない場合は、右方向を既定値として使用する。
- スナップショットに月蝕状態がない場合は空配列として描画し、古い状態との互換性を保つ。

## テスト戦略

### ユニットテスト

- 月蝕選択時の星形課題、45点の合格ライン、クールダウン。
- 吸引半径・移動量・中心から32pxの下限・ステージ境界補正。
- 固定向き、行動不能、レーザー最大3ヒットとダメージ式。

### 統合テスト

- スナップショットが月蝕状態を含み、補間後の描画入力を維持する。
- Godotヘッドレス起動時にパースエラーがないこと。

## 依存ライブラリ

新規依存は追加しない。

## 実装の順序

1. アイコン改名と候補ID・課題・クールダウンの追加。
2. サーバー権威とローカルの月蝕ルール実装。
3. スナップショット・描画・テストを追加し、Godotで検証する。

## セキュリティ考慮事項

- クライアント入力で月蝕の位置・向き・ダメージを指定できないよう、発動時のサーバー状態だけを用いる。

## パフォーマンス考慮事項

- 月蝕は各プレイヤーにつき同時に最大1件で、固定間隔の判定のみを行う。

## 将来の拡張性

- `lunar_eclipses` の状態は他の持続型スキルと同様に presentation ID を持つため、専用画像・音・粒子演出を後から追加できる。
