# オンライン対戦アーキテクチャとサーバー責務

最終更新: 2026-09-11（公開対戦サーバー改修反映）

## 1. 全体像

オンライン対戦は、Godot クライアント、Lobby API、Dedicated Serverで構成する。公開運用では、その前にPublic Gatewayを置く。試合の正はDedicated Serverであり、クライアントは入力を送信して受信した状態を表示する。Lobby APIは試合前の予約、接続情報の発行、運用監視を担当し、試合ルールは持たない。

```text
Godot クライアント A/B
│  HTTPS（公開時はPublic Gateway経由）
  ▼
Lobby API (FastAPI) ── SQLite
│  room / slot / nonce付き60秒有効token / ENet接続先
  │
  └───────────────────────┐
                          │ ENet / UDP
                          ▼
                  Dedicated Server (Godot headless)
                  └─ room ごとの MatchSession
                     └─ MatchSimulation（試合の正）

Dedicated Server ── HTTP（内部トークン付き）──> Lobby API
  心拍・受理／拒否イベントを監視用に記録
```

- Dedicated Server は既定で UDP 7000 を待ち受ける。`SKILL_BATTLE_SERVER_PORT` を設定すると変更できる。
- 1プロセスは最大10ルーム、1ルームは2人まで管理する。
- ローカル起動スクリプトでは UDP 17000 を使う。運用環境の Lobby API と Dedicated Server は systemd の別サービスとして起動する。
- 公開時はLobby APIとGatewayをloopbackで待ち受け、FunnelはGatewayの`127.0.0.1:8080`だけをHTTPS公開する。Dedicated ServerのUDPはplayit.ggから`127.0.0.1:7000`へ中継する。

## 2. Dedicated Server の責務

| 分類 | 実装されている責務 |
| --- | --- |
| 接続 | ENet 接続を受け付け、切断を検知する。 |
| 参加認証 | tokenのHMAC-SHA256署名、room ID、slot、有効期限をローカル検証した後、Lobbyでnonceを一度だけconsumeしてから参加させる。 |
| ルーム | peer ID と slot を紐付け、ルームごとに `MatchSession` を作る。 |
| 入力検証 | 移動・イベントの送信者、型、イベント種別、連番、連番の最大飛び幅を検証する。 |
| 試合進行 | accumulatorを使う固定60Hz tickで、移動、通常攻撃、課題、スキル、HP、時間切れ、勝敗を計算する。1フレーム最大5 tickまでcatch-upし、過剰な遅延分は破棄する。 |
| 状態同期 | 20Hzで、同じルームの参加者だけに `unreliable_ordered` のsnapshotを送る。古い状態は再送待ちにせず、最新状態を優先する。 |
| 切断処理 | 試合中に切断した slot は敗北として扱う。`duel` は相手の勝利で終了し、`free_for_all` は生存者が1人になるまで継続する。ロビー中の切断は対戦相手の離脱として扱い、残った参加者はロビーで待機を続ける。全員がいなくなったルームは破棄する。 |
| 運用通知 | 有効時は心拍と受理／拒否イベントを Lobby API へ送る。 |

Dedicated Server は、クライアントから座標、HP、命中、得点、勝敗を受け取らない。これらはすべて `MatchSimulation` が決定する。

## 3. Lobby API の責務

| 分類 | 現行の動作 |
| --- | --- |
| 稼働確認 | `GET /healthz` は `{ "ok": true, "protected_api_ready": true/false }` を返す。 |
| 公開API認証 | `/v1/*`は`X-Skill-Battle-Access-Token`を必須とし、一覧・作成・参加に別々のレート制限を適用する。 |
| ルーム作成 | `POST /v1/rooms` で名前（1〜48文字）を受け、slot 1 を60秒予約し、nonceを含む接続情報を返す。 |
| ルーム一覧 | `GET /v1/rooms` で`AVAILABLE`、`RESERVED`、`CONNECTING`、`CONNECTED`のルームと予約人数を返す。 |
| 参加予約 | `POST /v1/rooms/{room_id}/join` がSQLiteの原子的トランザクション内で空きslotとnonceを予約し、接続情報を返す。 |
| 接続情報 | room、slot、署名付き短期 token、Dedicated Server のアドレスとポートを返す。 |
| 状態遷移 | `AVAILABLE → RESERVED → CONNECTING → CONNECTED → RUNNING → CLOSED`を管理する。nonceのconsume、接続、開始、切断、終了は内部認証済みAPIだけが遷移させる。 |
| 期限処理 | `RESERVED`と接続前`CONNECTING` leaseだけを回収する。試合中の予約を期限だけで再公開しない。Dedicated Server再起動時は、前回プロセスの非終端roomを安全に`CLOSED`へ遷移する。 |
| 監視記録 | `POST /internal/server/updates` で Dedicated Server の心拍とイベントを SQLite に保存する。 |
| 管理画面 | 認証済みの `/admin` から監視情報、サービス状態、ログ、開始・停止・再起動を扱う。 |

`/internal/rooms/{room_id}/status`は`connected`、`disconnected`、`running`、`closed`を更新する内部APIである。Dedicated Serverはnonce consume成功、接続、試合開始、切断、終了をこのAPIへ通知する。Dedicated Serverの起動時は`/internal/server/reconcile`を呼び、前回プロセスが残した非終端roomを閉じてから新規入室を受け付ける。

## 4. 接続から試合終了まで

1. クライアントAが `POST /v1/rooms` を呼び、slot 1 の予約と接続情報を受け取る。
2. クライアントBが `GET /v1/rooms` で一覧を取得し、`POST /v1/rooms/{room_id}/join` で slot 2 を予約する。
3. 各クライアントが返された `server_address` と `server_port` に ENet 接続する。
4. 接続後、クライアントは reliable RPC の `join_room(room_id, slot, token)` を送る。
5. Dedicated Serverがtokenを検証し、Lobbyのnonce consume成功後に空いている指定slotへpeerを割り当てる。成功時は`joined_room`、失敗時は`join_rejected`を返す。
6. クライアントはロビー中にキャラクターと打鍵士のスキル2を `loadout` イベントで送り、各自が Ready を設定する。
7. 2人が接続済みで両者 Ready になった後、slot 1のホストがゲーム開始を要求すると、`MatchSession` が試合を開始する。
8. 試合中、クライアントは移動入力と単発イベントを送り、Dedicated Server が状態を更新して snapshot を送る。
9. HPが0、150秒の制限時間切れ、または切断で Dedicated Server が結果を確定する。HP 0 の場合だけは、入力を停止した `finish` phase を2秒間同期してから `result` phase へ遷移する。時間切れと切断は従来どおり直接 `result` phase へ遷移する。

試合終了後の再戦は、両者がリザルト画面で再戦を選択したときだけ開始する。どちらかがロビーへ戻るを選択した場合は、再戦選択を取り消して両者をロビーへ戻す。

`request_match_start()` は、両者のReadyがtrueであり、送信者がslot 1である場合だけ受理する。クライアントのゲーム開始ボタンはこのRPCを使う。

## 5. 通信契約

| 方向 | RPC / HTTP | 信頼性 | 内容 |
| --- | --- | --- | --- |
| Client → Lobby | `GET /v1/rooms` | HTTP | 公開ルーム一覧の取得。 |
| Client → Lobby | `POST /v1/rooms`、`POST /v1/rooms/{id}/join` | HTTP | 予約と接続情報の取得。 |
| Client → Dedicated | `join_room`、`set_room_ready` | reliable | 入室認証と Ready 状態。 |
| Client → Dedicated | `submit_match_input` | unreliable | 連番付きの移動ベクトル。座標は送らない。 |
| Client → Dedicated | `submit_match_event` | reliable | 連番付きの攻撃、課題、スキル、構成変更イベント。 |
| Dedicated → Client | `joined_room`、`join_rejected` | reliable | 入室結果。 |
| Dedicated → Client | `receive_skill_presentation` | reliable | スキル実体生成を一度だけ知らせる表示用イベント。命中・ダメージは含めず、サーバーの状態を変更しない。 |
| Dedicated → Client | `receive_dedicated_snapshot` | unreliable ordered | 表示用の試合状態。20Hz。古い状態より新しい状態を優先する。 |
| Dedicated → Lobby | `POST /internal/server/updates` | HTTP + 内部トークン | 心拍、参加、イベント、Ready、開始、切断、ルーム終了の監視記録。 |

### クライアントから送れるイベント

| イベント | payload | Dedicated Server 側の処理 |
| --- | --- | --- |
| `attack` | なし | 通常攻撃のクールダウン、距離、向き、命中を判定する。 |
| `small_skill` / `big_skill` / `skill3` | なし | 対応する課題を開始する。`skill3` は打鍵士だけが開始できる。 |
| `challenge_character` | 1文字 | タイピング課題の次の1文字を検証する。 |
| `challenge_submit` | 64文字以下の文字列 | 算術課題の回答を検証する。 |
| `challenge_trace` | 最大512点の座標列 | なぞり課題を採点する。 |
| `challenge_cancel` | なし | 自分の課題を失敗として終了する。 |
| `loadout` | `character` と `big_skill` | ロビー中だけ、キャラクターと打鍵士のスキル2を設定する。 |

移動・イベントは slot ごとに単調増加する連番を要求する。重複、逆行、最大120を超える飛び、未知のイベント、型違いの payload は受理しない。`loadout` 以外のイベントは試合中だけ受理する。移動入力は固定tickで15tick（0.25秒）更新されなければ停止入力へ戻す。

### snapshot に含むもの・含まないもの

snapshotには`server_tick`、`round_id`、slotごとの`input_acknowledgements`、フェーズ、Ready、各プレイヤーの位置・向き・HP・クールダウン等、残り時間、勝敗、状態テキスト、飛翔体・魔法陣・衝撃波・三叉震槌・分身・ハンマー回転の状態を含める。Dedicated Server はカウントダウン開始ごとに`round_id`を増やし、クライアントは新しい値を受信した時点で入力・イベントの送信連番を初期化する。クライアントは最新2件を短時間補間して表示する。フェーズ・Ready・勝敗・課題UIは最新snapshotを直ちに反映する。

課題の正解 `answer` は snapshot から必ず除外する。進行中課題の詳細（課題文、入力済み文字、なぞり目標・軌跡）は、その課題を行っている受信者本人にだけ送る。相手の集中状態はプレイヤー状態だけで表示する。プレイヤー状態も表示・HUDに不要なサーバー専用値を除外する。

スキル実体には`presentation_id`を付ける。生成時はreliableな表示用イベントで即時に開始を知らせ、snapshotは位置・寿命・発動済み状態の補正と復旧を担う。ハンマー回転などの連続演出はクライアントが描画時間で進め、snapshotの角度とは0/2π境界をまたぐ最短経路で補正する。命中・ダメージ・ノックバックは引き続きDedicated Serverだけが決定する。

## 6. 試合ルールの権威

`MatchSimulation` は画面、入力、ネットワークに依存しない共有ルール層である。1ルームにつき1つ持ち、次を正として保持する。

- 2人の位置、向き、HP、各種クールダウン、集中状態、装備
- 150秒の試合時間、試合終了フラグ、勝者
- 各プレイヤーの進行中課題と採点結果
- 飛翔体、魔法陣、衝撃波、三叉震槌、分身、ハンマー回転

キャラクターごとの課題と発動効果は次のとおりである。

| キャラクター | スキル1 | スキル2 | スキル3 |
| --- | --- | --- | --- |
| 打鍵士 | タイピング成功で鍵片弾 | タイピング成功で三叉震槌、または鍵片追弾II | タイピング成功で黄金大旋槌。60点以上では鍵片弾も追加する。 |
| 算術士 | 算術成功で分身と移動・通常攻撃強化 | 算術成功で透明化と強化状態 | なし |
| 詠唱者 | 円なぞり成功で遅延魔法陣3個 | 星形なぞり成功で放射状の貫通弾 | なし |

課題中は移動速度が半減する。被弾しても課題は中断されない。タイピング・算術は制限時間を持ち、詠唱者のなぞり課題は制限時間なしである。HPが0なら相手の勝利、150秒経過時は残HPの多い側の勝利、同値なら引き分けとなる。

## 9. 運用と既知の境界

- Dedicated Server の監視送信は、`SKILL_BATTLE_LOBBY_INTERNAL_URL` と `SKILL_BATTLE_INTERNAL_API_TOKEN` の両方を設定したときだけ有効になる。未設定では試合処理は継続し、監視だけ無効になる。
- 状態同期は完全な差分同期ではない。`unreliable_ordered`での欠落に安全に対応するため、各snapshotは単体で描画可能な状態を持つ。将来、差分同期を行う場合はクライアントごとのベースライン確認応答が必要になる。
- 有効時は5秒ごとに、稼働時間、アクティブルーム数、接続 peer 数、直近5秒の受理入力数・受理イベント数・拒否イベント数を心拍として送る。イベント履歴は Lobby 側に最大500件保存する。
- `/internal/*` は Caddy から外部公開しない。内部 API と管理 API はそれぞれ別のトークンで認証する。
- tokenはroom・slot・有効期限・nonceに束縛される。nonceはLobbyで一度だけconsumeされ、消費済みtokenは再利用できない。
- Lobbyの予約とDedicated Serverへの実参加は別の処理である。予約後にENet接続しなければ60秒で予約が失効する。consume後は短い`CONNECTING` leaseだけを回収対象とする。
- Dedicated Serverの通知によりLobbyのroom statusは接続・試合開始・切断・終了へ同期される。Dedicated Serverが再起動した場合、以前の非終端roomは安全にclosedとなる。

問題を切り分けるときは、次の順で確認する。

1. Lobby API で予約と接続情報を取得できたか。
2. UDP の Dedicated Server へ接続できたか。
3. `joined_room` を受信したか。失敗時は `join_rejected` の内容を確認する。
4. `receive_dedicated_snapshot` が20Hzで届いているか。
5. 管理画面で Dedicated Server の直近心拍とイベントを確認する。
## 対戦形式と定員

Lobby API は作成リクエストの `match_mode`（`duel` / `free_for_all`）を SQLite の room に保存する。`duel` は slot 1–2、`free_for_all` は slot 1–3 を予約できる。署名済みチケットには mode を含め、Dedicated Server はその値で `MatchSession` を生成する。

`MatchSession` の Ready・開始・再試合・snapshot は mode の slot 数を基準に処理する。snapshot は `match_mode`、`room_capacity`、各 player の `defeated` と `placement` を送信する。
