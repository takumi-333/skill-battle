# サーバー運用管理ダッシュボード仕様

## 目的

公開ロビーとDedicated Serverを毎回手作業で起動・観測する負担をなくす。運用者は認証済みのブラウザ画面から、2サービスの稼働状態、Dedicated Serverが受理した重要な処理、直近ログを確認し、限定したライフサイクル操作を実行できる。

## 運用モデル

- 本番では`skill-battle-lobby.service`と`skill-battle-server.service`をsystemdで`enable`し、OS起動時および異常終了時に自動起動する。日常の起動にシェル操作や環境変数の設定を要求しない。
- 管理画面はLobby Serverが`/admin`で提供する。公開ロビーAPIと画面は分離し、管理用トークンがないリクエストは受け付けない。
- 開始・停止・再起動は、固定した2サービスだけを対象にする。任意のコマンド・サービス名・ログ引数を画面から渡してはならない。
- systemdの制御は、`skill-battle`ユーザーに限定コマンドだけを許可するroot所有の制御スクリプトを`sudo`経由で実行する。Lobby Server自体をrootで動かさない。

## Windows開発用ランチャー

- `deploy/windows/start-local.bat`はWindows Explorerからダブルクリックして、ローカルLobby ServerとDedicated Serverをまとめて起動する。
- 初回は`.local-server/local.env`に必要なローカル秘密値を生成する。このディレクトリはGit管理対象外である。
- `deploy/windows/stop-local.bat`はランチャーが記録したPIDと開始時刻が一致するプロセスだけを停止する。
- Windowsランチャーはローカル開発用であり、本番Linuxのsystemd管理を置き換えない。

## Dedicated Serverの観測

Dedicated ServerはLobby Serverのローカル内部APIへ、5秒ごとの心拍と重要イベントを送る。心拍には少なくとも稼働時間、アクティブルーム数、接続peer数、直近区間の受理入力数・受理イベント数・拒否イベント数を含める。

イベントとして、入室の受理／拒否、試合イベントの受理／拒否、準備状態、試合開始、切断、空ルームの終了を保存する。連続入力はイベントごとに保存せず、心拍の集計値で確認する。

## 管理画面

管理画面は以下を表示する。

| 領域 | 表示・操作 |
| --- | --- |
| サービス | Lobby/Dedicatedのsystemd状態、PID、起動時刻、開始・停止・再起動 |
| Dedicated Server | 最終心拍時刻、稼働時間、アクティブルーム、接続peer、入力／イベント集計 |
| 受理履歴 | Dedicated Serverが送った直近の重要イベント |
| ログ | 各サービスの直近journalログ |

画面は短い間隔で状態を再取得し、通信失敗や心拍の欠落を明示する。`SKILL_BATTLE_ADMIN_TOKEN`をブラウザのセッション内にだけ保持して管理APIを呼ぶ。

## セキュリティ境界

- `SKILL_BATTLE_ADMIN_TOKEN`は管理画面のAPIを保護し、既存の参加token署名秘密鍵とは別にする。
- `SKILL_BATTLE_INTERNAL_API_TOKEN`はDedicated ServerからLobby Serverの内部観測APIへ送る共有秘密値とする。
- Caddyはインターネットから`/internal/*`を転送しない。Dedicated ServerはloopbackのLobby APIへ直接送る。
- すべての秘密値はsystemdの`EnvironmentFile`にだけ配置し、リポジトリ・画面・ログに出力しない。

## 非対象

- 試合入力の全パケット記録、任意コマンド実行、ユーザー管理、外部監視SaaS連携はこの機能の対象外とする。
